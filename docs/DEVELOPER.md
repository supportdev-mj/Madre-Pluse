# Madre Pulse — Developer Guide

## Setup

Prerequisites: Node 20 (see `.nvmrc`), Docker + Docker Compose, npm 10+.

```bash
# 1. Copy env files
cp .env.example .env
cp apps/api/.env.example apps/api/.env
cp apps/web/.env.example apps/web/.env

# 2. Install dependencies (root, workspaces)
npm install

# 3. Start infra + apps
docker compose up --build

# 4. Run migrations (first time, and after every schema change)
npm run db:migrate

# 5. Open the app
# Web:    http://localhost:3000
# API:    http://localhost:4000/health
# MinIO:  http://localhost:9001 (console)
```

For local (non-Docker) development of a single app:

```bash
npm run dev:api   # NestJS, port 4000, requires postgres/redis running (docker compose up postgres redis minio)
npm run dev:web   # Next.js, port 3000
```

## Architecture Overview

- **Monorepo**: npm workspaces — `apps/api` (NestJS), `apps/web` (Next.js App Router), `packages/shared` (zod schemas/enums shared by both).
- **Database**: PostgreSQL via Prisma ORM. Schema at `apps/api/prisma/schema.prisma`, migrations in `apps/api/prisma/migrations/`.
- **Task detail page** (`apps/web/src/app/tasks/[id]/page.tsx`, Slice 6, extended in Slice 7): read-only task header, Subtasks, Dependencies, Attachments, and a merged Activity+Comments feed. Reachable by clicking a task title in List view (Board/Calendar cards aren't linked yet — clicking would conflict with `@dnd-kit`'s drag handling on Board, and Calendar cells are already dense). Deliberately doesn't expose subtask-progress or blocked-count badges on List/Board/Calendar — that would need a batched aggregate query (`groupBy`/filtered `_count`) across every task in a list response, which isn't justified until a slice actually needs it at-a-glance; today it's one click away on the detail page.
- **Comments, attachments, and time entries are open collaboration, not edit rights.** Unlike subtasks/dependencies (gated by `assertCanModifyTask` — ADMIN/MANAGER or the task's assignee/creator), any authenticated org member can comment, attach a file, or log time on any task, matching "Chat = task-level comments only" from the architecture decisions — the point is letting anyone weigh in, not just the people formally on the task. Modifying is narrower and per-resource-owner: a comment's own author, an attachment's own uploader, or a time entry's own logger — or ADMIN/MANAGER (moderation) — in all three cases.
- **Time is stored as `minutes: Int`, never a float.** `TimeEntriesService` takes whole minutes; the frontend's "Hours" input (decimal, e.g. `1.5`) is converted client-side via `Math.round(hours * 60)` before validation. Capped at 1440 (24h) per entry as a sanity check, not a real-world limit — there's no running timer in Phase 1 (see Phase 2: Auto time tracking), so entries are always logged after the fact.
- **Activity feed is auto-logged, not hand-written.** `TasksService.create`/`update` diff the incoming change against the existing row and write a `TaskActivity` row per changed field (status/priority/assignee/dueDate) inside the same transaction as the task write — see `buildChangeActivities`. Messages store the raw before/after values (e.g. `"changed status from TODO to IN_PROGRESS"`), not a denormalized actor name — the actor is resolved live via the `actor` relation on every read, so a later name change doesn't strand stale text in old activity rows.
- **`apiFetch` must not force JSON `Content-Type` on `FormData` bodies** (`apps/web/src/lib/api-client.ts`) — the browser needs to set its own `multipart/form-data; boundary=...` header for file uploads, which it only does if no `Content-Type` is set at all. This bit us once already in Slice 7; the fix is a single `!(init.body instanceof FormData)` check in `request()`.
- **Task views**: `apps/web/src/app/tasks/page.tsx` holds shared state (tasks/members/projects, filters, the create form) and a List/Board/Calendar view toggle — all three read from the same filtered `tasks` array. `task-board-view.tsx` is the Kanban board (`@dnd-kit/core`, pointer-based — chosen over native HTML5 drag-and-drop since it's far more reliable to automate/test and more consistent across browsers); dragging a card calls the same `onStatusChange` handler as the list view's inline status dropdown, so there's one code path to `PATCH /tasks/:id`, and a card is only draggable if the viewer can edit that task. `task-calendar-view.tsx` is the month grid; tasks with no `dueDate` are simply not shown there. **Date handling gotcha deliberately avoided**: due dates are calendar dates, not instants, so the grid never converts a task's ISO due-date string through a local-timezone `Date` — it compares the raw `YYYY-MM-DD` slice of the ISO string against grid-day keys built purely from the local `Date` constructor's own Y/M/D (no UTC conversion crosses the comparison). Verified in a Playwright run with `timezoneId: 'America/New_York'` (UTC-4) — a task due Aug 25 would land on Aug 24 in the grid if this were done naively via `new Date(iso).getDate()`.
- **Multi-tenancy**: every org-scoped table carries `orgId`. The request-scoped tenant context (`nestjs-cls`, populated by `JwtAuthGuard` with `userId`/`orgId`/`role`) landed in Slice 1. Slice 2 settled the enforcement mechanism: **explicit `orgId` filtering in every service method** (via `requireOrgId(cls)`, see `apps/api/src/common/tenant/require-org-id.ts`), not a Prisma Client Extension. This was a deliberate choice over the originally-planned auto-scoping middleware — explicit `where: { orgId }` on every query is easier to audit/grep for a security-critical concern like tenant isolation, and avoids the correctness pitfalls of blanket query-rewriting (nested writes, raw queries, and relation loads silently bypassing an extension). Every new org-scoped model/service must follow the same pattern: `findFirst({ where: { id, orgId } })` before any update/delete (returning 404, not 403, so cross-tenant probing can't distinguish "not found" from "not yours"), and `orgId` set explicitly in every `create`. `Organization` itself has been the tenant root since Slice 0 (`docker-compose.yml`'s Postgres holds all tenants in one schema, isolated only by `orgId`, not separate databases/schemas per tenant — the standard "shared database, shared schema" multi-tenancy pattern, appropriate at this scale). Slice 17 added the first piece of *self-service* tenant management on top of that isolation — see `OrganizationsService` below.
- **Superadmin (Slice 18)**: deliberately *not* another value in the `Role` enum. `Role` (`ADMIN`/`MANAGER`/`USER`) lives on `Membership` — it's scoped to one org. A superadmin is a platform operator who isn't necessarily a member of any particular org at all, so it's a separate flag, `User.isSuperAdmin`, checked independently by a separate `SuperAdminGuard` (not `RolesGuard`/`@Roles`). It rides along in the JWT (`isSuperAdmin` claim, set at login/refresh from the DB) and into CLS the same way `role` does, but `AdminService` (the one controller gated by `SuperAdminGuard`) deliberately does **not** call `requireOrgId` — it's the one place in the app meant to see across every tenant, and it returns account/plan metadata only (name, slug, plan, status, member count), never a tenant's actual task/project/comment data. That boundary is a design choice, not a technical limitation — expanding it would need a deliberate, separate decision.
- **Google OAuth connection (Slice 19)**, step 1 of meeting-notes-to-tasks: each org's ADMIN connects the org's own Google Workspace from `/settings` — not something a superadmin does on the tenant's behalf (see the plan's clarifying discussion). `GoogleIntegrationController.callback` is the one route in the whole app with no `JwtAuthGuard` at all — Google redirects the raw browser there with no `Authorization` header, so CSRF protection comes entirely from a short-lived (10m) `state` JWT minted by `connect-url` and verified in the service, the same `JwtService` the rest of auth uses (now exported from `AuthModule` for this reason). `access_type=offline&prompt=consent` is required on the auth URL — without `prompt=consent`, Google silently omits the refresh token on a second authorization by the same account, which is exactly the token this integration needs to keep working after the user's browser session ends. Implemented with plain `fetch()` against Google's OAuth/userinfo endpoints rather than the `googleapis` SDK — this slice only makes two or three simple REST calls; that package (and the heavier Drive API client it brings) is worth adding once the actual transcript-polling step needs it, not before.
- **Auth**: bcrypt-hashed passwords, JWT access token (15m default) + rotating refresh token (random 320-bit token, sha256-hashed at rest, httpOnly+sameSite=lax cookie scoped to `/auth`, 30d default). Refresh rotation detects reuse of an already-rotated token (signals theft) and revokes the user's whole token family. See Slice 1 (`apps/api/src/auth/`).
- **Realtime** (`apps/api/src/realtime/realtime.gateway.ts`, Slice 9): a Socket.io gateway. The client connects with `auth: (cb) => cb({ token: getAccessToken() })` (see `apps/web/src/lib/notifications-context.tsx`) — a callback, not a static value, so a reconnect always picks up the latest access token rather than one captured at connect time. `handleConnection` verifies the JWT the same way the REST `JwtAuthGuard` does (same secret, same payload shape) and joins the socket to `user:{userId}` and `org:{orgId}` rooms; an invalid/missing token disconnects the socket immediately rather than leaving it half-authenticated. Only `user:{userId}` is used so far (personal notifications); the `org:{orgId}` room exists for a future feature that needs org-wide broadcast.
- **Background jobs** (Slice 9): BullMQ on Redis, via `@nestjs/bullmq`. `BullModule.forRootAsync` in `app.module.ts` parses `REDIS_URL` into `{ host, port, password }` (`config/redis-connection.ts`) since BullMQ's `connection` option doesn't accept a raw `redis://` URL string. Two queues: `email` (one job per notification, decouples SMTP round-trip time from the request that triggered it) and `due-soon` (a single repeatable job, `{ repeat: { every: 3600000 }, jobId: 'due-soon-scan' }` registered in `DueSoonModule.onModuleInit` — the fixed `jobId` is what stops every app restart from registering a duplicate schedule).
- **Reports** (`apps/api/src/reports/`, `apps/web/src/app/reports/page.tsx`, Slice 12): one productivity table, one row per active member — tasks completed, on-time rate, total time logged, and average time per completed task, all optionally scoped to a `from`/`to` date range. Two things worth being precise about: "total time logged" sums every `TimeEntry` the member logged in the date range (any task, reflecting overall activity in that window), while "avg time per task" sums `TimeEntry` minutes only for the specific tasks that were *completed* in the range (regardless of when that time was logged) divided by how many completed — mixing those two would make the average meaningless, so they're computed from different queries on purpose. **"PDF export" is the browser's print-to-PDF, not a server-side PDF library.** `GET /reports/productivity.csv` returns a real generated file (hand-rolled CSV escaping — quotes/commas/newlines — no library needed for something this small); there's no equivalent PDF endpoint. Instead the report page is print-optimized (Tailwind `print:` variants hide the nav and filter controls, force black-on-white for the table) and a "Print / Save as PDF" button just calls `window.print()`. This was a deliberate call, same reasoning as the dashboard's hand-rolled charts: a real PDF library (pdfkit, puppeteer, etc.) is a meaningfully heavier dependency than this feature justifies when the browser already does it for free.
- **Manager dashboard** (`apps/api/src/dashboard/`, `apps/web/src/app/dashboard/page.tsx`, Slice 11): a single `GET /dashboard` aggregates status counts (`groupBy`), overdue count + a 10-item preview list, tasks completed in the last 7 days, an org-wide on-time rate, and per-active-member workload (open/overdue/done counts) — all computed server-side in one request rather than the frontend stitching together several list endpoints. Gated ADMIN/MANAGER on both ends: `RolesGuard` on the controller, and the page also checks `role` before firing the request (redundant with the guard by design — the point is not showing a 403 flash to a USER who lands on the URL directly). Charts are hand-rolled `<div>` bars with inline `width: %` styles (a stacked bar for status distribution, a bar per member for workload) — no charting library. That's a deliberate call, not an oversight: these are simple proportional bars, not the kind of interactive/animated chart that would justify a new dependency, and Phase 1 has otherwise avoided adding libraries unless the feature is genuinely hard to hand-roll (the one exception being `@dnd-kit` for Slice 4's drag-and-drop).
- **`Task.completedAt`** (Slice 11): added because "completed this week" and "on-time rate" can't be computed from `updatedAt` (which changes on *any* field edit, not just a DONE transition) or from string-matching `TaskActivity` messages (fragile). `TasksService.computeCompletedAt()` sets it on the TODO/IN_PROGRESS → DONE transition and clears it on the reverse; `ReopenRequestsService.decide()` also clears it on approval, since that path moves a task off DONE without going through `TasksService.update()`. Both call sites need to agree on this or the dashboard's numbers silently drift.
- **Reopen approval workflow** (`apps/api/src/reopen-requests/`, Slice 10): a `ReopenRequest` is a small state machine — `PENDING` → `APPROVED`/`REJECTED`, and once decided it's terminal (`decide()` 400s on a non-`PENDING` request; there's no re-deciding or un-approving). Requesting reuses `assertCanModifyTask` (same rights as editing the task) and is only valid when the task is `DONE`; only one `PENDING` request per task at a time (409 on a second). Deciding is `ADMIN`/`MANAGER`-only via `RolesGuard`, not an in-service check, matching every other admin-gated route in this codebase. Approval updates the task's status to `TODO` and the `ReopenRequest` row in the same `$transaction`, plus a `TaskActivity` row, so the task detail page's existing feed shows the reopen without any new UI plumbing. Both the request (notifies every `ADMIN`/`MANAGER` in the org, not just one) and the decision (notifies the requester) go through `NotificationsService.notify()` from Slice 9 — two new triggers on the same pipeline, no new delivery mechanism.
- **Notifications** (`apps/api/src/notifications/`, Slice 9): `NotificationsService.notify()` is the single entry point other services call — it writes the `Notification` row, pushes it over the socket, and enqueues the email job, so there's exactly one place that defines what "notify a user" means. Three triggers wired so far: `TasksService` on assignment (create or reassign, skipping self-assignment), `CommentsService` on a new comment (to the task's assignee and creator, excluding the commenter, deduped if they're the same person), and `DueSoonService.scan()` (tasks due within 24h, not `DONE`, with an assignee — skips a task+user pair that already got a `TASK_DUE_SOON` notification in the last 24h, so the hourly job doesn't spam on every run). Email is best-effort: `EmailService` checks whether `SMTP_HOST` is set and logs the message instead of sending when it isn't — the current dev `.env` ships with it empty on purpose, so **no real emails send out of the box**; set real SMTP_* values to change that.
- **File storage** (`apps/api/src/storage/storage.service.ts`, Slice 7): a thin wrapper over the AWS S3 SDK, pointed at MinIO in dev and real S3 in production — same code path either way, since MinIO implements the S3 API (`forcePathStyle: true` is required for MinIO compatibility). This replaced the originally-planned separate "local disk driver" — MinIO already fills that role in dev, so a second parallel backend would be pure duplication with no one actually running the app without Docker. **`StorageService` holds two S3 clients**, and mixing them up silently breaks downloads: `client` (env `S3_ENDPOINT`) does the real work — upload/delete/bucket-management — and in Docker Compose that's `http://minio:9000`, a hostname that only resolves inside the Docker network. `publicClient` (env `S3_PUBLIC_ENDPOINT`, always `http://localhost:9000` in dev) is used *only* to sign download URLs, because a presigned URL's signature is bound to the host it was signed for — sign it with the internal hostname and the browser gets a URL it can never resolve. Bucket is auto-created on `onModuleInit` if missing (`HeadBucket` then `CreateBucket`), so there's no manual MinIO console step for a fresh dev environment.

Realtime: connect Socket.io to the API's base URL with `auth: { token: <accessToken> }`; the server emits a `notification` event (payload: `NotificationSummary`) to the connecting user whenever `NotificationsService.notify()` fires for them.

Access tokens go in the `Authorization: Bearer` header (not a cookie) so they're never sent automatically by the browser; only the refresh token is a cookie, and it's httpOnly + scoped to path `/auth`. The frontend keeps the access token in memory only (`apps/web/src/lib/api-client.ts`) and calls `/auth/refresh` on load and on any 401.

## Database Schema

Current models (through Slice 19):

- `Organization` — tenant root. `id, name, slug, plan (FREE/PRO/ENTERPRISE, Slice 18), status (ACTIVE/SUSPENDED, Slice 18), createdAt`. `plan` is a label only — nothing enforces limits by plan yet, and it's not wired to real billing (still Phase 3). `status: SUSPENDED` is enforced at `/auth/login` and `/auth/refresh` (see `AuthService.assertOrgActive`).
- `User` — global identity (not tied to a single org). `id, email, passwordHash, name, initials, avatarColor, isSuperAdmin (Slice 18, default false), createdAt, updatedAt`. `isSuperAdmin` is a platform-wide flag, independent of any `Membership`/`Role` — someone can be a superadmin and also hold any normal role in any org at the same time. **No API or UI sets this flag** — it's deliberately not self-service (see Known limitations for how to set it).
- `Membership` — join of User↔Organization, carries `role` (`ADMIN`/`MANAGER`/`USER`) and `status`. Unique on `(userId, orgId)`.
- `RefreshToken` — `id, userId, tokenHash (unique, sha256), expiresAt, revokedAt, replacedById, createdAt`. One row per issued refresh token; rotation on each `/auth/refresh` marks the old row revoked and links `replacedById` to the new one.
- `Client` — org-scoped tag/filter entity (no portal). `id, orgId, name, notes, createdAt, updatedAt`. Unique on `(orgId, name)`.
- `Project` — org-scoped, optionally tagged to a `Client` (`onDelete: SetNull`, so deleting a client never orphans a project). `id, orgId, clientId, name, description, status (ACTIVE/ARCHIVED), createdAt, updatedAt`. Unique on `(orgId, name)`.
- `Task` — org-scoped. `id, orgId, projectId, createdById, title, description, status (TODO/IN_PROGRESS/DONE), priority (LOW/MEDIUM/HIGH/URGENT), dueDate, completedAt, createdAt, updatedAt`. `projectId` is optional and `onDelete: SetNull`; `createdById` is required and set from the JWT at creation (never client-supplied). `completedAt` (Slice 11) is auto-managed, not client-settable — see the dashboard architecture note. Had a single nullable `assigneeId` through Slice 13; Slice 14 replaced it with `TaskAssignment` below.
- `TaskAssignment` (Slice 14) — join table for a task's collaborators, replacing the old single `Task.assigneeId`. `id, taskId, userId, createdAt`, both relations `onDelete: Cascade`. Unique on `(taskId, userId)` so the same person can't be added twice. Every assignee has identical edit rights on the task (same as the old sole assignee) and gets notified the same way; see `TasksService.update`'s diffing logic for how the assignee list is replaced wholesale on `PATCH` and who gets notified.
- `Subtask` — belongs to one `Task` (`onDelete: Cascade`). `id, taskId, assigneeId, title, done, createdAt, updatedAt`. No org-scoping of its own; access is gated through the parent task. `assigneeId` (Slice 15, nullable, `onDelete: SetNull`) is the individual owner of that piece of work on a shared task — validated to be one of the parent `Task`'s current assignees (`TaskAssignment` rows), but purely informational: it doesn't restrict who can toggle or reassign the subtask, which stays governed by the same `assertCanModifyTask` rights as the rest of the task.
- `TaskDependency` — a directed edge `taskId -> dependsOnId` meaning `taskId` is blocked by `dependsOnId` (both `onDelete: Cascade`). `id, taskId, dependsOnId, createdAt`. Unique on `(taskId, dependsOnId)`. See `DependenciesService.wouldCreateCycle` for the cycle check.
- `Comment` — belongs to one `Task` (`onDelete: Cascade`). `id, taskId, authorId, body, createdAt, updatedAt`.
- `Attachment` — belongs to one `Task` (`onDelete: Cascade`). `id, taskId, uploadedById, fileName, mimeType, sizeBytes, storageKey (unique), createdAt`. `storageKey` is `{orgId}/{taskId}/{random}-{sanitizedFileName}` in the bucket — the actual file bytes live in S3/MinIO, not the database.
- `TaskActivity` — belongs to one `Task` (`onDelete: Cascade`). `id, taskId, actorId, type (CREATED/STATUS_CHANGED/PRIORITY_CHANGED/ASSIGNEE_CHANGED/DUE_DATE_CHANGED), message, createdAt`. Auto-written by `TasksService`, never client-supplied.
- `TimeEntry` — belongs to one `Task` (`onDelete: Cascade`). `id, taskId, userId, minutes, note, date, createdAt, updatedAt`. `date` is the calendar day the work was done, independent of `createdAt` (when the entry was logged).
- `Notification` — org-scoped, always personal to one `User` (`onDelete: Cascade` on both `Organization` and `User`). `id, orgId, userId, taskId (nullable), type (TASK_ASSIGNED/NEW_COMMENT/TASK_DUE_SOON/REOPEN_REQUESTED/REOPEN_APPROVED/REOPEN_REJECTED), message, read, createdAt`. `taskId` is nullable and `onDelete: Cascade` — if the task is later deleted, its notifications go with it rather than pointing at nothing.
- `ReopenRequest` — belongs to one `Task` (`onDelete: Cascade`). `id, taskId, requestedById, reason, status (PENDING/APPROVED/REJECTED), reviewedById (nullable), reviewNote (nullable), createdAt, reviewedAt (nullable)`. `requestedBy` and `reviewedBy` are separate `User` relations (`ReopenRequester`/`ReopenReviewer`) since a request and its review are different people.
- `BlockerReport` (Slice 16) — belongs to one `Task` (`onDelete: Cascade`). `id, taskId, reportedById, reason, status (OPEN/RESOLVED), resolvedById (nullable), resolutionNote (nullable), createdAt, resolvedAt (nullable)`. Deliberately shaped like `ReopenRequest` (same two-actor pattern via `BlockerReporter`/`BlockerResolver` relations) but simpler — a two-state flag rather than a decision with an approve/reject branch, and not gated to any particular `Task.status` (you can be blocked at any stage, not just when done). `reason` is free text, independent of the formal `TaskDependency` "blocked by" links from Slice 6 — reporting a blocker doesn't require one to exist.
- `GoogleIntegration` (Slice 19) — one per `Organization` (`orgId` unique), `onDelete: Cascade`. `id, orgId, googleEmail, refreshTokenEncrypted, connectedById, lastSyncedAt (nullable, reserved for the transcript-polling job — not written yet), createdAt, updatedAt`. `refreshTokenEncrypted` is a genuine secret that must be decrypted and reused later (unlike `RefreshToken`'s one-way hashed tokens, only ever compared for equality) — encrypted at rest with AES-256-GCM via `common/utils/encryption.ts`, keyed by `TOKEN_ENCRYPTION_KEY`. First piece of the meeting-notes-to-tasks pipeline (see the architecture note below); `MeetingNote`/`TaskDraft` models are intentionally not built yet — added only when the ingestion step that needs them is.

This is Phase 1's full target schema — every model named in the original plan now exists.

## Security: RBAC/tenant audit (Slice 13)

A full static pass over every controller and service in `apps/api/src`, done as part of hardening. Methodology and findings, so a future pass can pick up where this left off rather than re-deriving it:

- **Every `findUnique`/`findFirst`/`update`/`delete` call was checked for tenant scoping.** Pattern used throughout: services either filter directly by `{ id, orgId }`, or — for resources nested under a task (subtasks, dependencies, comments, attachments, time entries, reopen requests) — filter by `{ id, taskId }` *after* `getTaskOrThrow(taskId, orgId)` has already confirmed that `taskId` belongs to the caller's org. That second form is safe by transitivity, not an oversight: once the parent task is confirmed in-org, every child lookup scoped to that `taskId` inherits the guarantee. Verified this ordering holds (task check strictly before child lookup) in every mutating method across `subtasks`, `dependencies`, `comments`, `attachments`, `time-entries`, and `reopen-requests` services.
- **Two intentional exceptions to `requireOrgId`, both confirmed safe:**
  - `NotificationsService` scopes by `userId` (from CLS), not `orgId` — correct and *stricter* than org-scoping, since notifications are personal (see the Notifications architecture note).
  - `DueSoonService.scan()` queries tasks with no `orgId` filter at all — it's a scheduled BullMQ job with no request context to read an org from, so it necessarily scans across every org in one pass. Tenant isolation is preserved per-notification: each one is created with the *candidate task's own* `orgId`, never a caller's. Commented in the code so this doesn't look like a missed scope to a future reader.
- **`DependenciesService.wouldCreateCycle`'s BFS has no `orgId` filter on its `taskDependency.findMany` calls**, which is also safe, by a less obvious invariant: every `TaskDependency` row is created only after *both* endpoints (`taskId` via `getTaskOrThrow`, `dependsOnId` via an explicit org-membership check) are confirmed to be in the same org — so by construction, no edge ever crosses an org boundary, and a BFS starting from an in-org task can only ever reach other in-org tasks.
- **Every controller has `JwtAuthGuard` at minimum** (class-level on all of them except `HealthController`, which is intentionally public, and `AuthController`, where only `/auth/me` is guarded since register/login/refresh/logout are necessarily unauthenticated entry points). ADMIN/MANAGER-only routes carry `RolesGuard` + `@Roles(...)`, either per-route (`clients`, `projects`, `members`, `tasks` DELETE, `reopen-requests` decide) or class-level where *every* route needs it (`dashboard`, `reports`).
- **`assertCanModifyTask` coverage matches design intent exactly**: called in every mutating method of `subtasks` (create/update/remove — 3 of 3) and `dependencies` (create/remove — 2 of 2) services, and in `TasksService.update` — but deliberately *not* in `TasksService.remove` (gated by `RolesGuard` instead, since delete is admin/manager-only, stricter than edit rights) or `ReopenRequestsService.decide` (same reasoning — deciding is admin/manager-only by design, not a task-edit-rights action).
- **Comments, attachments, and time entries have no `RolesGuard`** on any route by design (open collaboration — see the Slice 7/8 architecture notes) — their delete methods do an in-service ownership-or-moderator check instead of a route-level role restriction, since the permission depends on *whose* resource it is, not a fixed role list.

No missing authorization checks were found. This audit is static analysis only — it hasn't been paired with a live penetration-style test (e.g., an actual two-org curl session probing every mutating endpoint), which is still worth doing as a follow-up, on top of the standard per-slice cross-tenant checks already run for Slices 1–8 and the live functional verification pass now done for Slices 9–13 (see Known limitations).

## Production Docker & AWS deployment (Slice 13)

**Local dev is unaffected.** `docker-compose.yml` now pins both services to `target: dev` explicitly (`apps/api/Dockerfile` and `apps/web/Dockerfile` each gained a `prod` stage *after* `dev`, and without an explicit target Docker defaults to the *last* stage — pinning `dev` means adding the prod stage can never silently change what `docker compose up` builds). Neither Dockerfile's `prod` stage is wired into compose at all; they're meant to be built directly (`docker build --target prod ...`) by CI/CD for pushing to ECR.

**API prod image** (`apps/api/Dockerfile`, `prod` stage): a real multi-stage build — `prod-deps` installs with `--omit=dev` (so `prisma` had to move from `devDependencies` to `dependencies`; it's needed at runtime to run migrations and regenerate the client, not just at build time), `build` compiles TypeScript using the full `deps` stage, and the final `prod` stage copies only the compiled `dist/`, the pruned `node_modules`, and the Prisma schema — then runs `prisma generate` once more directly against the pruned `node_modules` rather than trying to copy generated engine artifacts across stages, which is more robust against hoisting-path assumptions. Runs as the built-in non-root `node` user (Alpine Node images ship this user specifically for this).

**Web prod image** (`apps/web/Dockerfile`, `prod` stage): uses Next.js's `output: 'standalone'` (`next.config.js`) — the build step traces actual imports and produces a self-contained server with its own pruned `node_modules`, so the runtime stage needs no dependency install of its own, just three `COPY --from=build` lines (standalone output, `.next/static`, and `public/` — the latter two are deliberately excluded from the standalone trace by Next.js itself and must be copied in by hand, a well-documented gotcha for anyone adapting this later). Also runs as `node`, not root.

**`NEXT_PUBLIC_*` vars are inlined into the JS bundle at build time, not read at container runtime.** The web `prod` stage declares `ARG NEXT_PUBLIC_API_URL` / `ARG NEXT_PUBLIC_SOCKET_URL` (defaulting to the local dev URLs) specifically so CI/CD can pass the real values via `--build-arg` — setting them as plain container environment variables on a already-built image would do nothing, since by then they're already baked into the JS. This is a classic Next.js Docker mistake; worth remembering if this pattern gets copied elsewhere.

**Migrations are a separate step, not baked into the container's `CMD`.** The API prod image's `CMD` just starts the server (`node dist/src/main.js`) — it deliberately does not run `prisma migrate deploy` on boot, because ECS Fargate services normally run multiple task replicas, and several containers racing to apply the same migration on startup is exactly the kind of thing that causes hard-to-reproduce production incidents. Apply migrations as a one-off ECS `RunTask` (same image, override the command to `npx prisma migrate deploy` from `/app/apps/api`) as a step in the deploy pipeline, before the new service revision starts taking traffic.

**Gotcha found by actually running the `prod` image (not just building it): the compiled entrypoint is `dist/src/main.js`, not `dist/main.js`.** `apps/api/tsconfig.json`'s `include` array spans two different top-level directories (`src/**/*.ts` and `prisma/seed.ts`), so TypeScript infers the package root — not `src/` — as `rootDir`, and `nest build`'s compiled output preserves the `src/` prefix instead of flattening it away. The build itself succeeds either way; only `docker run` against the image surfaces it, as `Error: Cannot find module '/app/apps/api/dist/main.js'`. Both `apps/api/Dockerfile`'s `prod` stage `CMD` and `apps/api/package.json`'s `start` script are fixed to point at `dist/src/main.js` / `dist/src/main`. Worth remembering if `tsconfig.json`'s `include` ever changes shape again — `rootDir` inference is sensitive to it.

**AWS shape** (per the architecture decisions on record — ECS Fargate, RDS, ElastiCache, S3, ALB): two Fargate services (`api`, `web`) behind an ALB, `api`'s target group on `/health` for the health check already built in Slice 0. RDS Postgres replaces the `postgres` container; ElastiCache Redis replaces `redis` (used by both BullMQ and, when Slice 9's queues run, the `due-soon` repeatable job — note that a repeatable job registered via `onModuleInit` re-registers on every task restart, which is safe since BullMQ dedupes by the fixed `jobId`, but means it must stay pointed at the *same* Redis instance across deploys or you'd get duplicate schedules). S3 replaces MinIO directly — `StorageService`'s dual-endpoint design (Slice 7) becomes simpler in AWS, not more complex: point `S3_ENDPOINT` and `S3_PUBLIC_ENDPOINT` at the same place, or better, leave both env vars pointed at a CloudFront distribution in front of the bucket if using a CDN, and omit any custom `endpoint` override entirely so the AWS SDK uses its normal regional S3 endpoints — the internal-vs-public split only existed to work around MinIO's Docker-network-only hostname, which doesn't apply once it's real S3. Secrets (`JWT_*_SECRET`, `S3_SECRET_KEY`, `SMTP_PASS`, DB credentials) belong in AWS Secrets Manager or SSM Parameter Store, injected as task-definition secrets — never baked into the image or committed to `.env`.

**Both `prod` stages are now confirmed built and run-tested locally** (`docker build --target prod ...` for both `apps/api` and `apps/web`, then `docker run` against the built images on the existing dev-stack network) — this is what surfaced the entrypoint-path bug above. After the fix: the API container starts, connects to Postgres/Redis, and serves `/health` with 200, running as the non-root `node` user; the web container serves the homepage, static assets, and `public/robots.txt` correctly. AWS itself remains untested — there's no AWS account wired up yet — so the ECS/RDS/ElastiCache/S3/ALB shape above is still a documented starting point, not a deployed pipeline, but the container images themselves are no longer unverified.

## Known limitations (tracked, not blocking)

- **`packages/shared` isn't watched.** It has a real build step now (`tsc` → `dist/`, required because NestJS's dev runtime executes plain compiled JS and can't load raw `.ts` via `require`). Docker bind-mounts the source over the image's build output, so after editing `packages/shared/src`, run `npm run build --workspace=packages/shared` on the host and restart the `api`/`web` containers to pick it up — it won't hot-reload automatically.
- **Multi-org membership has no UI.** The schema allows a `User` to hold multiple `Membership`s, but `/auth/login` just picks the oldest active one — there's no org switcher. Not needed until a slice introduces invites to multiple orgs.
- **JWT role claim can go stale.** A role change takes effect on next token refresh (≤15m), not instantly, since the access token embeds `role` at issuance.
- **`POST /members` still has no real invite email.** Slice 9 added email delivery infrastructure, but nothing wires a `POST /members` call to send one — the temporary password is still only returned once in the API response. Wiring that up is a small follow-up, not a new feature.
- **Projects have no hard delete.** `PATCH /projects/:id { status: 'ARCHIVED' }` is the only removal path, to avoid ever orphaning a Task once Slice 3 adds `Task.projectId`.
- **No real SMTP configured in dev.** `SMTP_HOST` ships empty in `apps/api/.env`; `EmailService` detects that and logs the would-be email instead of sending it. This is intentional (see the Notifications architecture note above), not a bug — set real SMTP_* env vars to get actual delivery.
- **Slices 9–11's migrations were briefly missing from the database — found and fixed.** Those three slices were built while Docker was down, so `prisma migrate dev` (which needs a live DB) never ran for the `Notification`/`ReopenRequest` models or `Task.completedAt`, even though `prisma generate` (schema-only, no DB needed) had already succeeded and made `lint`/`build` pass clean — a reminder that a clean build doesn't guarantee the DB schema is in sync. Once Docker was back, `docker compose run --rm api npx prisma migrate dev --name add_notification_reopen_completedat` generated and applied the missing migration; the DB is now fully in sync with `schema.prisma`.
- **Slices 14, 15, and 16's combined migration is now applied — with a manual backfill, because Docker's non-interactivity forced a different path than usual.** `prisma migrate dev` refused to run at all (`"Prisma Migrate has detected that the environment is non-interactive"` — it wants a TTY to confirm destructive changes, which isn't available via a scripted `docker compose exec`). Worked around it with the documented non-interactive alternative: `prisma migrate diff --from-url "$DATABASE_URL" --to-schema-datamodel prisma/schema.prisma --script` to get the raw SQL, hand-edited it to insert a backfill (`INSERT INTO task_assignments ... SELECT ... FROM tasks WHERE "assigneeId" IS NOT NULL`) *before* the `DROP COLUMN "assigneeId"` line — otherwise Prisma's default diff just drops the old column outright, silently discarding whichever tasks still had a single assignee set the old way — then applied it with `prisma migrate deploy` (the non-interactive command `migrate dev`'s own error message points at). Confirmed all 4 pre-existing test tasks kept their assignment (`SELECT count(*) FROM task_assignments` → 4). Worth remembering any time a migration needs to run in a non-interactive shell: `migrate diff --script` + manual edit + `migrate deploy`, not `migrate dev`.
- **Slice 18's migration (`User.isSuperAdmin`, `Organization.plan`/`status`) is written but not yet applied — Docker's down again.** No backfill needed this time (all three are new columns with schema defaults — `isSuperAdmin` false, `plan` FREE, `status` ACTIVE — so existing rows just pick up the default, nothing to migrate data-wise). Same non-interactive path as above applies: `migrate diff --script` → `migrate deploy` (not `migrate dev`) once Docker's back.
- **There is no API or UI to make someone a superadmin — by design.** Self-service superadmin escalation would be a real security hole (any org admin could otherwise try to grant themselves platform-wide access). Set it directly against the database once a user account exists: `UPDATE users SET "isSuperAdmin" = true WHERE email = '...';` (psql, Prisma Studio, or any DB client). There's deliberately no other path.
- **Slice 19's migration (`GoogleIntegration` table) is written but not yet applied — Docker's still down.** A brand-new table, no backfill needed — same non-interactive `migrate diff --script` → `migrate deploy` path as the slices above.
- **Connecting Google Workspace needs real setup on Google's side before it can work at all — nothing here is testable yet.** `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`/`GOOGLE_REDIRECT_URI`/`TOKEN_ENCRYPTION_KEY` all ship empty in `.env.example`; without them, "Connect Google Workspace" in Settings fails with a clear "not configured" error (same pattern as `SMTP_HOST`), rather than the app crashing. To actually use it: create a Google Cloud project → OAuth consent screen → an OAuth 2.0 Client ID of type "Web application" → add `GOOGLE_REDIRECT_URI`'s exact value to that client's "Authorized redirect URIs" → put the resulting client ID/secret in `.env` → generate `TOKEN_ENCRYPTION_KEY` with `openssl rand -base64 32`. None of this can be done from inside this codebase — it's an account-level action only the org (or whoever manages Madre Pulse's own Google Cloud project) can take.
- **Only the OAuth connection exists so far — nothing reads a transcript yet.** Slice 19 is step 1 of the meeting-notes-to-tasks feature: an org can connect and disconnect Google Workspace, and that's the full extent of it. Polling Google Drive for new Meet transcripts, formatting them into minutes, and drafting tasks from them are separate, not-yet-built steps — see `docs/MANAGEMENT.md`'s Slice 19 row for the planned shape.
- **Docker Desktop has been repeatedly unstable this session — containers get silently recreated from stale images.** Twice now, the entire `madre_pluse` container set vanished between one check and the next (`docker ps -a` showed none of them, only unrelated leftover containers) even though nothing in this project's tooling stopped them — almost certainly Docker Desktop itself restarting/resetting under the hood (a `docker system df` call surfaced a storage-driver filesystem error, `lstat ... no such file or directory`, consistent with the disk-full trouble from earlier in the project). The dangerous part: `docker compose up -d` after a wipe recreates containers from whatever image was last built, which can be **stale** if source changed since that build (e.g., a schema change) — the container looks like it's running, but the API fails to even compile, and the symptom in the browser is a bare "Failed to fetch" with no useful error. A one-off fix via `docker compose exec` (regenerating the Prisma client, applying the migration by hand) only patches the *running container* — it's lost the moment Docker recreates it again. The real fix is `docker compose build api web` so the correct source and generated Prisma client are baked into the *image* itself, then `docker compose up -d --force-recreate api web`. If "Failed to fetch" reappears after everything was working, check `docker ps -a` for a suspiciously recent `Up X seconds/minutes` on containers that were supposedly already running — that's the tell.
