| 21 | Minutes of Meeting (MoM): PDF upload → AI-extracted task queue | Upload a MoM PDF, AI extracts action items into a review queue, accept/edit/reject before it becomes a real Task | Done | Built independently of Slices 19-20 above, with a different design: the AI key is per-org (`OrgAiSettings`, ADMIN-managed from Settings, own Anthropic key/cost per tenant) rather than the platform-wide `LlmSettings`. `MomExtractionService` sends the uploaded PDF to Claude as a native `document` content block (not OCR/text-extraction first) with a two-pass prompt — an initial exhaustive extraction, then an independent self-check pass that re-reads the same document hunting specifically for anything the first pass missed (buried-in-prose items, no explicit owner, etc.) — since a single LLM pass over a long document isn't reliably exhaustive. `MomService.upload()` dedupes extracted items against already-queued candidates and existing task titles (normalized match), resolves each item's stated "responsible" name against active org members (only auto-assigns on an unambiguous single match), stores the PDF in S3/MinIO, and creates one `MomUpload` + one `MomTaskCandidate` per surviving item. Review queue (`/mom` page, `MomTaskCandidate.status` PENDING/ACCEPTED/REJECTED): ADMIN/MANAGER see every candidate, a plain USER only the ones the AI matched to them; accepting requires title/description/dueDate/assignee all filled in first (via the Edit modal) and creates a real `Task` through the normal `TasksService.create()` path — same activity log and notifications as a hand-created task — linking back via `createdTaskId`; rejecting just marks it `REJECTED` for audit. |

New `meeting-sync` module: `GoogleMeetApiService` (plain `fetch()` wrapper over the Meet REST API v2 — `conferenceRecords.list` → `transcripts.list` (state ENDED/FILE_GENERATED) → `transcripts.entries.list` + `participants.list` to resolve speaker names into a `Speaker: text` transcript), `MeetingSyncService.syncOrg()` (one org, used by both paths below) and `.syncAllConnectedOrgs()` (every connected org, one failure logged and skipped rather than aborting the rest), a BullMQ repeatable job (`meeting-sync` queue, every 15 minutes, same fixed-`jobId` pattern as Slice 9's `due-soon` job) plus a `POST /integrations/google/sync` (ADMIN only) for an immediate manual run from the new "Sync now" button on Settings. Synced meetings show in `/mom` with a video-camera icon instead of a document icon, otherwise identical review flow to a PDF upload. **Not live-verified**: no real Google Cloud OAuth app with Meet API access this session, and Docker Desktop was unreachable for a live migration dry-run, so `prisma/migrations/20260909130000_add_mom_upload_google_meet_source/migration.sql` was hand-written (mirroring Prisma's own generated style from Slice 21's migration) rather than machine-diffed — run `prisma migrate diff` against a real dev DB and compare before trusting it in production |

## Architecture decisions on record

- Stack: TypeScript, Next.js + NestJS, PostgreSQL (Prisma), Redis/BullMQ, Socket.io
- Hosting: AWS (ECS Fargate, RDS, ElastiCache, S3, ALB), Docker for local + prod
- Multi-tenant SaaS, no billing in Phase 1
- Client = internal tag/filter only, no external client portal
- Chat = task-level comments only, no standalone chat module
- Build order = vertical full-stack slices (DB → API → UI per feature)
